# แผนทำงานอย่างไร — milestone · การ์ด · หลักฐาน

สถานะไม่เคยพิมพ์ด้วยมือ คำนวณจากไฟล์สามชนิด:

| ไฟล์ | เก็บอะไร | ใครเขียน |
|---|---|---|
| `docs/plan/milestones/M<n>.md` | เป้าหมาย · ขอบเขต · ประตูออก · ลำดับการ์ด · `status` (`active` ได้ทีละอัน) | designer · {{owner}}อนุมัติ |
| `docs/plan/tasks/M<n>/T-M<n>-<nn>.md` | การ์ดหนึ่งใบ: frontmatter + หัวข้อ "เกณฑ์ผ่าน" ที่ทุกข้อเป็นคำสั่ง | designer |
| `docs/plan/evidence/<id>.json` | จุดเริ่ม · ผลของคำสั่ง · ไฟล์ที่เปลี่ยน | เครื่องมือเท่านั้น (`task:start` · `task:verify`) |

`docs/plan/STATE.md` และ `.saf/plan.md` สร้างจากไฟล์ข้างบน (`{{cmd.taskState}}`) · ห้ามแก้ด้วยมือ

## 1. รอบการ์ด

```
{{owner}}กด Go ที่ milestone
  → designer เขียนการ์ด (+ สเปกพร้อมฉากยอมรับ)                         /saf-plan
  → ทีละการ์ดตามลำดับ:
      {{cmd.taskStart}}                       บันทึก commit เริ่มต้นและไฟล์ที่ค้างอยู่ก่อน
      implementer ทำการ์ด (แตะเฉพาะไฟล์ใน touch)
      {{cmd.taskVerify}}                      รันทุกคำสั่งใน "เกณฑ์ผ่าน" · ไฟล์ที่เปลี่ยนอยู่ใน touch · มี test ของฉากยอมรับ
      spec-reviewer เทียบงานกับสเปก (อ่านอย่างเดียว)
      qa-runner รัน test จริงเมื่อการ์ดแตะ UI / multiplayer / ประสิทธิภาพ
      commit (หรือ {{cmd.taskMerge}} สำหรับการ์ดสาย)
  → {{cmd.taskVerifyM}}                       ประตูออก → รายงาน → {{owner}}ปิด milestone
```

การ์ด **เสร็จ** เมื่อ `task:verify` ผ่านเท่านั้น · ไม่ผ่าน = การ์ดยังเปิดและบันทึกเหตุผล (คำสั่งที่ล้ม · ไฟล์นอก `touch` ·
ไฟล์ใน `dont_touch` · ฉากที่ไม่มี test)

ความถี่ที่ test **ทั้งชุด** รันคือ `workflow.testMode` (`every-card` · `targeted` · `milestone` · ค่าเริ่มต้น
`milestone`) · ในโหมดที่เลื่อน การ์ดพิสูจน์ตัวเองด้วย test ของมันเอง หลักฐานจะมีคำว่า "full suite deferred to gate"
(เลื่อนไปที่ประตู) · ในโหมด `milestone` ประตูออกรัน test ทั้งชุดเสมอ ส่วนในโหมด `targeted` test ทั้งชุดรันตอนรวมการ์ดสาย
(ถ้าประตูล้ม `{{cmd.taskCulprit}}` หาการ์ดที่ทำให้ล้ม) · แต่ละคนเปลี่ยนโหมดในเครื่องตัวเองได้ด้วย `SAF_TEST_MODE`
หรือไฟล์ `saf.config.local.json` ที่ git ไม่ track (ใส่ได้ `workflow.testMode` · `workflow.lanes.code` ·
`workflow.sideLanes.max` · `models.effort` · key อื่นรวมถึง `$schema` ถูกปฏิเสธ) · เพดาน lane ไม่มีตัวแปรสภาพแวดล้อม (ทุก session
ต้องนับเพดานเดียวกัน) และตั้งได้ไม่เกิน `LANE_CEILING` ใน `tools/saf/lib/config.mjs`

## 2. รูปแบบการ์ด

คัดลอก [tasks/_template.md](tasks/_template.md) · ช่องใน frontmatter:

| ช่อง | ความหมาย |
|---|---|
| `id` · `milestone` · `title` | `T-M1-01` · `M1` · หนึ่งบรรทัด · ชื่อไฟล์ = id · โฟลเดอร์ = milestone |
| `spec` | ไฟล์สเปกที่การ์ดนี้ทำ (`docs/specs/…`) |
| `depends` | การ์ดที่ต้องผ่านก่อน |
| `size` | `M` (≤ {{sizeM}} บรรทัดโค้ด · test ≤ {{testM}}) หรือ `L` (≤ {{sizeL}} · test ≤ {{testL}}) — `task:verify` ล้มเมื่อเกิน {{hardStop}} เท่าของเพดาน → แตกการ์ด |
| `role` | ใครทำ: {{roleNames}} |
| `repo` | `.` (ค่าเริ่มต้น) หรือ path ของ git submodule — หนึ่ง submodule ต่อการ์ด |
| `touch` | glob ของไฟล์ที่การ์ดแก้ได้ (บังคับ) |
| `dont_touch` | glob ที่ต้องไม่เปลี่ยนแม้ `touch` ครอบ |
| `scenarios` | รหัสฉากยอมรับ (`AUTH-AC-01`) — แต่ละรหัสต้องมี test ที่มีรหัสในชื่อ |

หัวข้อ "เกณฑ์ผ่าน": ทุกข้อเป็นหนึ่งคำสั่ง (คำสั่งใน backtick ต้นข้อ หรือทั้งบรรทัด) · ต้อง exit 0 ทุกข้อ

การ์ด L มีหัวข้อ "ขั้นตอน" (`## ขั้นตอน` หรือ `## Steps`) เป็นรายการที่มีเลขกำกับด้วย · แต่ละขั้นคืองานที่ commit เดียวทำให้เสร็จได้ และ `{{cmd.taskStateCheck}}` ไม่ยอมรับการ์ด L ที่มีขั้นตอนน้อยเกินไป (การ์ด M จะมีหัวข้อนี้ก็ได้ แต่ไม่มีอะไรตรวจ) · จบแต่ละขั้นด้วยหนึ่ง commit ที่หัวเรื่องมี `<รหัสการ์ด> step <k>/<n>` (`<n>` = จำนวนขั้นตอน) เช่น `feat(M4): T-M4-03 step 2/4 server routes` · การ์ดที่หยุดกลางทางเริ่มต่อที่ขั้นแรกที่ยังไม่มี commit แบบนั้น (`git log --oneline <commit เริ่มต้น>..HEAD`) · `task:verify` รันครั้งเดียวหลังขั้นสุดท้าย · `{{cmd.taskDiff}}` แบ่งไฟล์ diff ที่มันเขียนตาม commit เหล่านั้น — หนึ่งส่วนต่อหนึ่งขั้น แล้วส่วนสุดท้ายเป็นงานหลัง commit ของขั้นสุดท้าย{{#if tokenSaving.reviewerDiff}} — reviewer อ่านทีละส่วนและบอกว่าข้อพบแต่ละข้ออยู่ในขั้นไหน{{/if}}

## 3. milestone และประตูออก

ไฟล์ milestone มี `status: planned | active | paused | done` · `cards:` (ลำดับ = ลำดับทำ) และ `gates:`
แต่ละประตูมี `id` · `text` · `run:` (ไม่บังคับ) — ประตูที่ไม่มีคำสั่ง = {{owner}}ตรวจเอง
`{{cmd.taskVerifyM}}` รันทุกประตูแล้วเขียน `docs/plan/evidence/<M>.json` · `{{cmd.taskReport}}` เขียนรายงาน (`--html` เขียนหน้าเว็บเพิ่มสำหรับคนที่ไม่อ่าน JSON)

มีแต่{{owner}}ที่เปลี่ยน milestone เป็น `active` (กด Go) หรือ `done`
{{#if sideOn}}

### สายข้าง

งานที่ไม่ขึ้นกับ milestone ที่ active (หน้าเว็บแนะนำ · ตั้งชุมชน · เว็บเอกสาร) ทำคู่ขนานไปได้
designer ใส่การ์ดเหล่านั้นใน `side_cards:` ของ milestone ที่ยัง **planned** (ทุกใบต้องอยู่ใน `cards:` ด้วย):

```yaml
status: planned
cards: [T-M3-01, T-M3-02, T-M3-03]
side_cards: [T-M3-01]
```

- การ์ดสายข้างเริ่ม · ตรวจ · รวม · ผ่านผู้ตรวจ แบบเดียวกับการ์ดอื่นทุกอย่าง — สเปก · `touch` · `depends` · เพดานขนาด · หลักฐานเท่าเดิม
- milestone ที่ active มาก่อนเสมอ: `{{cmd.taskNext}}` ไล่การ์ดของมันก่อนการ์ดสายข้าง (มีป้าย `[สายข้าง M<n>]`)
  และการ์ดสายข้างเริ่มได้เฉพาะในที่ว่างที่ milestone ที่ active เหลือไว้
- การ์ดสายข้างที่กำลังทำพร้อมกันได้ไม่เกิน {{workflow.sideLanes.max}} ใบ (`workflow.sideLanes` ใน `saf.config.json` — เพดานของโปรเจกต์ · แต่ละเครื่องตั้ง `workflow.sideLanes.max` ของตัวเองได้ใน `saf.config.local.json` และไม่เพิ่มช่องเกินที่เพดาน lane เหลือ · ไม่เกิน `LANE_CEILING` ไม่มีตัวแปรสภาพแวดล้อม)
- การ์ดสายข้าง depends ได้เฉพาะการ์ดที่เสร็จแล้วหรือเริ่มได้เอง
- `docs/plan/STATE.md` และสรุปตอนเปิด session แสดงสายข้างเป็นบล็อกของตัวเอง · การ์ดสายข้างไม่นับในจำนวนเสร็จและประตูออกของ
  milestone ที่ active — นับเมื่อ milestone ของมันเองเป็น active
- คำสั่งทดสอบหนักของสายข้างต่อคิวกุญแจวัดผลเดียวกับงานอื่น
{{/if}}

## 5. สายขนาน

การ์ดของบทบาทที่ทำงานใน **สายโค้ด** ({{#each roles}}{{#eq .lane "code"}}`{{.name}}` {{/eq}}{{/each}}) ทำขนานได้ แต่ละใบอยู่ใน
git worktree ของตัวเองใต้ `{{workflow.worktreeDir}}/` บน branch `{{workflow.branchPrefix}}<id>` · การ์ดอื่นทำในโฟลเดอร์หลักทีละใบ

- `{{cmd.taskNext}}` บอกชุดการ์ดที่เริ่มพร้อมกันได้ (`touch` ไม่ทับกัน · เพดาน: สายโค้ด {{workflow.lanes.code}} · โฟลเดอร์หลัก {{workflow.lanes.main}}{{#if workflow.solo}} · path ที่ต้องทำเดี่ยว {{workflow.solo}}{{/if}}) และเหตุผลของใบที่ต้องรอ — เพดานเหล่านี้เป็นของโปรเจกต์ แต่ละเครื่องตั้ง `workflow.lanes.code` ของตัวเองได้ใน `saf.config.local.json` · (ไม่เกิน `LANE_CEILING` ใน `tools/saf/lib/config.mjs` และไม่มีตัวแปรสภาพแวดล้อมสำหรับเพดาน) · โฟลเดอร์หลักยังทำทีละใบ เพราะ `{{cmd.taskVerify}}` นับทุกไฟล์ที่เปลี่ยนในโฟลเดอร์ตั้งแต่ commit ตอนเริ่มเป็นของการ์ดนั้น จึงแยกการ์ดสองใบไม่ได้
- `{{cmd.taskStartLane}}` เปิดสาย: ไฟล์การ์ดต้อง commit แล้ว · หลักฐานถูก commit บน branch หลัก ·
  ขั้น 3–5 ล้ม = exit 6 — แก้ต้นเหตุแล้วรันใหม่ด้วย `--resume`
- ในสาย: ทำงาน แล้ว `{{cmd.taskVerify}}` (เขียนหลักฐานบน branch ของสายเท่านั้น) · `{{cmd.taskEnv}}` บอกพอร์ตของสาย
- กลับโฟลเดอร์หลัก: `{{cmd.taskMerge}}` รวมทีละใบ รันตรวจตอนรวม ({{mergeChecksText}}) แล้วสร้างสถานะใหม่ ·
  exit 3 = ปฏิเสธ (ยังไม่ผ่าน / โฟลเดอร์หลักไม่สะอาด) · 4 = ชน (ย้อนการรวมแล้ว) · 5 = ตรวจตอนรวมล้ม (ย้อนการรวมแล้ว)
- เมื่อ `workflow.testMode` = `milestone` การตรวจตอนรวมข้าม test ทั้งชุด (ประตูออกเป็นคนรัน) · ถ้าประตูล้ม `{{cmd.taskCulprit}}` หาการ์ดที่ทำให้ล้ม

## 7. กฎของหลักฐาน

- "เสร็จ" = รันจริง แนบผลของคำสั่ง ห้ามคาดเดาหรือติ๊กช่อง
- `docs/plan/evidence/` เครื่องมือเขียนเอง ห้ามแก้หรือลบด้วยมือ
- test ที่ผลไม่นิ่ง ให้แก้ความไม่นิ่งก่อน — ห้ามรันซ้ำจนเขียวแล้วเรียกว่าเสร็จ

## 8. Friction log

เมื่อ workflow เองขวางการทำการ์ด ให้จดลง `docs/plan/friction.md` ไฟล์เดียว เขียนต่อท้ายได้อย่างเดียว ชนิดที่ใช้:
`review-bounce` (รีวิวสเปกตกเพราะช่องโหว่ของ SAF ไม่ใช่เพราะงานของการ์ด) · `command-failed` (คำสั่งของ engine ล้ม พัง หรือทำผิด) ·
`doc-drift` (เอกสาร การ์ด หรือ template ขัดกับโค้ด) · `workaround` (งานต้องมีขั้นตอนที่ workflow ไม่รองรับ)

- เพิ่ม: `{{cmd.taskFrictionAdd}}` เขียนหนึ่งบรรทัดลงวันที่วันนี้ (ตาม `people.timeZone`) แล้วพิมพ์ id ออกมา · `--card <id>` ผูกกับการ์ดในแผน · `area` บอกว่าปัญหาอยู่ตรงไหน (เช่น `task:merge` หรือ path ของไฟล์) · ห้ามมี ` · ` หรือขึ้นบรรทัดใหม่ในช่องใดเลย
- ปิด: `{{cmd.taskFrictionClose}}` เพิ่มบรรทัดปิด: `carded` กับ `fixed` ต้องมี id การ์ดที่อยู่ในแผน ส่วน `dropped` ต้องมีเหตุผล รายการที่เป็น `fixed` หรือ `dropped` แล้วปิดซ้ำไม่ได้
- `{{cmd.taskFriction}}` ที่ไม่ใส่อาร์กิวเมนต์ แสดงรายการที่ยังเปิดกับที่ออกการ์ดแล้ว พร้อมจำนวนของแต่ละสถานะ
- ห้ามแก้หรือลบบรรทัดเดิม ถ้าผิดให้ปิดด้วย `dropped` (แล้วเพิ่มรายการใหม่ถ้าจำเป็น) บรรทัดที่รูปแบบผิดนับเป็นปัญหาของแผน — `{{cmd.taskStateCheck}}` บอกเลขบรรทัด
- คำสั่งเขียนแค่ไฟล์และไม่ commit — ให้ commit แยกต่างหาก `git commit -m "chore(plan): friction F-<nnn>" -- docs/plan/friction.md`
{{#if lanesOn}}
- `add` กับ `close` ถูกปฏิเสธในโฟลเดอร์งานของสาย: agent ในสายใส่บรรทัด `friction:` ไว้ในรายงาน แล้ว session หลักเป็นคนบันทึก
{{/if}}
- ตราบที่ยังมีรายการเปิดหรือออกการ์ดแล้ว สรุปตอนเริ่ม session จะแสดงบรรทัด `Friction: ค้างอยู่ <จำนวน> · ออกการ์ดแล้ว <จำนวน> — ดูด้วย <คำสั่ง>`

npm ส่งอาร์กิวเมนต์หลัง `--`: `npm run task:start -- T-M1-01`
{{/if}}
