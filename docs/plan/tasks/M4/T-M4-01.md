# T-M4-01 — Setup and upgrade install pinned skill packs

## Why

Moved from M2 (was T-M2-23) by D-013, then from M3 (was T-M3-14) to M4 by owner order 2026-11-25 so 0.2.0 could ship
without it. 0.2.0 ships only the format and `saf pack show` (T-M3-13).

`pack show` lets a person inspect a pack; this card installs the ones they pinned, and refuses changed content until a
person reviews it again. **Security-relevant:** build and review with the `security-review` skill — the writes must stay
inside `.claude/skills/<pack skill>/` and a hash mismatch must never change installed files.
[Spec rules 8–12](../../../specs/skill-packs.md#install-setup-and-upgrade) and
[rules 14–17](../../../specs/skill-packs.md#install-safety-from-the-t-m3-13-review) — the second set is the "MUST" list
the T-M3-13 review carried to this card ([notes](../../notes/M3-review-notes.md)), because this card is the first that
writes pack content into a project.

## What to do

- schema: `skills.external` — array of `{ path: non-empty string, sha256: 64 lowercase hex }`, no extra properties;
  `config.mjs` DEFAULTS `skills.external: []`
- `kit/tools-saf/lib/choices.mjs`: `skills.external` in `NOT_ASKED` (en + th one-liners) so SETUP-AC-01 holds until
  T-M4-02 moves it into the interview
- `kit/tools-saf/lib/packs.mjs` (rules 14–17, from the T-M3-13 review):
  - open each installed file and `saf-pack.json` once with `O_NOFOLLOW` (`fs.constants.O_NOFOLLOW ?? 0` — Windows has
    no such flag; there the `lstat` before and the `fstat` after the open must agree on device, inode and type) and
    check the open handle with `fstat` (regular file, within `PACK_LIMITS`)
  - hash the same bytes that were read and keep their decoded text (LF, leading BOM dropped, as the hash reads them)
    on the result, so the installer copies exactly what was hashed — today `readText` and `packHash` read each file
    separately
  - the "inside `.claude/skills/`" check compares `realpath` of the pack folder with `realpath` of the project's
    `.claude/skills` (a symlinked parent folder passes today's path check, `packs.mjs` near `readPack`)
- `kit/tools-saf/lib/generate.mjs`: `skillFiles` adds, per entry, the files of `readPack(root-resolved path,
  { taken })` — run again at install time, never trusting an earlier `pack show`; `taken` = core skills, kit packs,
  `saf-setup` and the skills of earlier entries — when valid and the hash equals the entry; rendered with the project
  data from the text `readPack` returned; dests under `.claude/skills/<skill>/` (assert the real parent of each
  resolved dest stays inside the project's real `.claude/skills/<skill>/`); an entry that is invalid, missing or
  mismatched adds no planned files and its already-installed files (from the manifest `packs` record) are carried as
  kept so `retireUnplanned` never removes them for that reason; warning with the reason (mismatch: new hash + changed
  file names from comparing rendered content with the manifest); manifest gains `packs: { <name>: { path, version,
  sha256, skills } }`; works in `planSetup` (setup and dry run) and in `refreshKitFiles` (upgrade)
- `docs/config-reference.md`: `external` in the `skills` section; `docs/skills.md`: how to add a pack (submodule,
  `pack show`, the entry, what happens on a changed hash) and drop the "installing comes in a later release" and "do not
  add the entry yet" sentences; `docs/upgrade.md`: one bullet
- `test/unit/skill-packs-install.test.mjs`: temp projects and fixture packs; one test per scenario id in its name; the
  symbolic-link cases skip with a reason where the OS refuses to create a link (Windows without the privilege), never
  pass silently; `test/unit/skill-packs.test.mjs` only if a `readPack`/`packHash` change needs its tests adjusted
- run `npm run saf:refresh`
- `CHANGELOG.md`: one line under `## Unreleased` (`### Added`) for what this card ships

## Out of scope
