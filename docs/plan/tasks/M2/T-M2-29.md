# T-M2-29 — A keep request is never ignored; a broken config stops upgrade before it writes

## Why

Two surprises found by the M2 spec reviews ([M2-review-notes.md](../../notes/M2-review-notes.md) notes 21/2 and
18/5, triage section 2). Both are cheap to fix and could cost the person their work or leave a half-upgraded project.

1. `saf setup --keep=CLAUDE.md` — the `=` form this CLI uses elsewhere (`spec-matrix --complete=a,b`) — is silently
   ignored: the setup parser only looks at the bare `--keep` token. The real run then archives and replaces `CLAUDE.md`.
   `--keep ","` (or `" , "`, `""`) splits to an empty list and keeps nothing, also silently.
   [Spec rule 15](../../../specs/setup-rerun.md#seeing-it-first).
2. With a `saf.config.json` that is not valid JSON, `upgrade()` in `src/install.mjs` first replaces `tools/saf/` and
   the setup skill (`copyKit`), then `mergeUpgradeScripts` warns, then `refreshKitFiles` reads the config with a `{}`
   default — `validateConfig({})` passes, so `/saf` commands and skills are re-rendered with default settings and no
   warning — and finally `upgrade()` calls `JSON.parse` on the same file unguarded and crashes with a stack trace. The
   project is left half-upgraded. [Spec rule 23](../../../specs/setup-rerun.md#upgrade-with-a-broken-config-upgrade-in-srcinstallmjs).

## What to do

- `kit/tools-saf/bin/saf.mjs`, `setup` case: any argument that starts with `--keep=` → usage error; a `--keep` value
  that holds no path after `split(",")` + trim → usage error. Both use the existing usage line and return 2 before
  anything is read or written. The header comment and the usage line show the same synopsis (note 21/8:
  `[--dry-run [--diff]]` vs `[--dry-run] [--diff]` — pick the header's form for both)
- `src/install.mjs`, `upgrade()`: right after `readVersion`, before `copyKit`, read `saf.config.json` when it exists;
  when it is not valid JSON or its root is not an object, log one line — `✗ saf.config.json is not valid JSON —
  upgrade changed nothing; fix it and run upgrade again` (non-object root: "is not a JSON object") — and return
  `{ before, after: before, report: null, errors: [that line], scripts: null }` so `bin/cli.mjs` exits 1 without a
  stack trace. Take the file name from the kit's `config.mjs` `CONFIG_FILE` (import it from `KIT`), not a typed
  string. Reuse the parsed object for the final `validateConfig` call instead of a second unguarded `JSON.parse`
- `kit/tools-saf/lib/generate.mjs`, `refreshKitFiles`: when `saf.config.json` exists but cannot be read as an object,
  push the warning `saf.config.json is not valid JSON — commands and skills were not refreshed` and return; a missing
  file keeps today's `{}` default (rule 23, last sentence)
- `docs/upgrade.md`: one line next to the `--dry-run --diff` sentence — the diff shows what the files hold, so never
  keep secret values in `CLAUDE.md` or the other generated files (spec rule 14)
- `test/unit/setup-guards.test.mjs`: RERUN-AC-10 and RERUN-AC-11 (ids in the test names). Both must fail on the code
  before this card: AC-10 because `--keep=CLAUDE.md` exits 0 and archives `CLAUDE.md`; AC-11 because upgrade throws
  and `tools/saf/` has already been replaced. For AC-11 make the old engine copy recognisable (for example a marker
  file inside `tools/saf/`) and assert it is still there after the refused upgrade
- run `npm run saf:refresh` and `node bin/cli.mjs upgrade --dir examples/todo-api`, then restore
  `examples/todo-api/.claude` and `examples/todo-api/package.json`

## Out of scope

- Supporting the `--keep=` form (refusing it is the fix; the spec keeps one form)
- `.saf/manifest.json` read with a `{ files: {} }` default, a missing `saf.config.json`, other unknown setup flags
  (notes 12/7, 13/12) — carried to M3
- Any change to `mergeUpgradeScripts` wording (note 18/2)
