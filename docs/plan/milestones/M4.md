# M4 — Skill packs and reinstall

## Goal

A team can bring its own skill pack from a local folder, pin it by content hash and have setup and upgrade install it
— and nothing changed is installed until a person looks again. Reinstalling SAF into a project that already has a plan
no longer moves the plan away. These three cards were cut from M3 by owner order 2026-11-25 ("เอาตามแนะนำ") so 0.2.0
could ship; 0.2.0 has the skill-pack format and the read-only `saf pack show` (T-M3-13) only.

## Scope

- **Install pinned packs** ([spec](../../specs/skill-packs.md) rules 8–12 and 14–17, D-013): T-M4-01 (was T-M3-14) —
  `skills.external` in the schema and defaults, setup, dry run and upgrade install each valid entry whose hash matches,
  a mismatch or missing folder keeps installed files byte-identical and warns, the manifest records each pack.
  **Carries the T-M3-13 review's MUST list** ([notes](../notes/M3-review-notes.md), spec rules 14–17, PACK-AC-08),
  because this is the first card that writes pack content into a project:
  - open each installed file and `saf-pack.json` with `O_NOFOLLOW` and check the open handle with `fstat` (Windows has
    no `O_NOFOLLOW`: `lstat` before and `fstat` after the open must agree)
  - hash the same bytes that are copied — read once, hash, render and write that decoded text (today `readText` and
    `packHash` read each file separately)
  - compare `realpath` of the pack folder with `realpath` of the project's `.claude/skills` (a symlinked parent folder
    passes today's path check)
  - pass the `taken` names (core skills, kit packs, `saf-setup`, skills of earlier entries) to `readPack`
  - re-validate everything at install time — never trust an earlier `pack show`

  So `kit/tools-saf/lib/packs.mjs` is in the card's `touch` (it was `dont_touch` in T-M3-14)
- **Interview** ([spec](../../specs/skill-packs.md) rule 13): T-M4-02 (was T-M3-15) — group 5 asks for pack folders,
  runs `pack show` for each, asks "Install this pack?" Yes · No with no recommended answer
- **Reinstall keeps the plan** ([spec](../../specs/setup-rerun.md) rule 37, review note 02/F2): T-M4-03 (was T-M3-26)
  — **waits for D-019** (proposed; options a · b · c, recommended a). The card is written for (a); its first "Done
  when" command fails until the owner marks the row decided. If he picks (b) or (c), the designer rewrites the card
  and rule 37 first
- Every card builds and is reviewed with the `security-review` skill (T-M4-01 and T-M4-02) · every card runs
  `npm run saf:refresh` and lists `npm run saf:refresh -- --check` in "Done when" · every card adds its own line under

- Sizes: all three are M. T-M3-15 and T-M3-26 were written as S; under D-021 a planned milestone's cards are M or L,

## Risks

- **Skill packs are third-party instructions:** a malicious skill can tell an agent to run commands even without
  scripts. The trust model limits what SAF does (no fetch, no run, `.md` only, pinned hash, explicit yes after
  `pack show`) but cannot vet the text — the docs and the interview say so
- **Writes into the project from a folder SAF does not own:** link swaps and a time gap between check and copy are the
  attack; spec rules 14–17 close them (one read per file, no-follow open, real-path containment). On Windows the
  no-follow guarantee is weaker (no `O_NOFOLLOW`); the `lstat`/`fstat` agreement is the fallback — reviewers check it
- **0.2.0 text that points ahead:** `saf pack show` prints "Entry for skills.external in saf.config.json … before you
  add the entry", but the 0.2.0 config check refuses the key; `docs/skills.md` says not to add it yet. T-M4-01 makes
  the printed text true — release M4 before telling users to add entries
- **D-019 stays open:** T-M4-03 cannot pass verify until the owner decides; the milestone cannot close without it
  (gate `cards`) — the owner may instead move T-M4-03 on, as he did here
